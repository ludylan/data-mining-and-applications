# 設計哲學 (Design Philosophy)

> 寫給**組員**，也寫給 **AI 助手**。
> 給 AI 的用法：把這份文件和 `docs/MAP.md` 一起貼給它，再說「我想新增/修改 XXX，請依照這份哲學指引我」。

## 0. 一句話
**LLM 負責判斷，流程與風控由程式鎖住。組員只管自己的外掛，不必懂整張圖。**

## 1. LangGraph 在這裡的角色
- **State (狀態)** = 全隊共用的黑板，是契約。節點只讀自己需要的欄位、只寫自己負責的欄位。
- **Node (節點)** = 一個做一件事的函式：讀 State，回傳「要更新的欄位」（不是整個 State）。
- **Edge (邊)** = 節點的先後順序。
- **Subgraph (子圖)** = 把一群節點包成一個節點。主圖用它保持簡潔，多 Agent 的複雜度都關在裡面。
- 不確定時：**多一個子圖，優於主圖多一個節點。**

## 2. 十條原則

1. **主圖小而穩。** 只有 觀察 → 決策 → 記錄。想加東西？先問能不能做成外掛或子圖。
2. **外掛優先於改圖。** 新觀察放 `observers/`，新提取放 `retrievers/`，用裝飾器登記，零接線。
3. **證據不下結論。** 一篇文件拆成多條證據，保留概要、要點、原文三層。`stance`（偏多/偏空/不確定）只用來分群檢索，**不計票、不加總**。多空由決策 Agent 綜合判斷。
4. **資訊漸進展開。** AI 先看概要（便宜），需要時才展開要點與原文（昂貴）。概要要寫得寧可多保留，也不要丟失資訊。
5. **時間是第一公民。** 每條證據有 `published_at` 與 `visible_at`。所有查詢都帶 `as_of`，只能看到 `visible_at <= as_of` 的內容。**這是防前視偏差的唯一防線，不要繞過它。**
6. **攝取與決策分開。** 資訊隨時可以進來（觀察），決策依固定節奏（每天至少交一份報告，調倉每日上限 25 次）。財報發布只會觸發觀察，不會改變決策節奏。
7. **AI 判斷，程式鎖規則。** 止損、權重上限、每日 25 次等寫在 `rules.py`，在 LLM 之後執行，AI 無權覆蓋。
8. **壞了也要跑完。** 每個節點和外掛都有錯誤隔離：一個壞掉，其他照跑，錯誤寫進報告的「錯誤與警告」。每天一定有報告。
9. **每次執行都可回看。** `runs/<時間>/` 裡有每個節點的輸出與 `report.md`。出問題先看這裡。
10. **沒有 API key 也能跑。** 所有節點要有 stub 行為。模型由 `config.toml` 按角色指定，程式裡只用 `get_llm("角色")`。

## 3. 文字線與數值線
- **文字線**：新聞、財報 → 爬蟲 / 關鍵字 / 萃取 → 證據條目。
- **數值線**：技術指標、傳統機器學習 → **不要硬轉成文字**，包裝成「數據工具」讓 Agent 查詢（規劃中）。
- 兩條線最後都只是 Agent 手上的工具。

## 4. 記憶層
- 現在：SQLite + FTS5（全文檢索，單一檔案，零安裝）。
- 未來要向量檢索：只改 `memory.py` 內部，保留 `add / search / get` 的簽名，外掛不受影響。
- 證據只增不改。想修正就新增一條。

## 5. 決策層
- 現在：多方 → 空方 → 裁判 → 硬規則，全是 stub。
- 趨勢策略重因果與趨勢，不逐檔細究：看事件傳導到哪些 ETF、漲幅是否已反映、哪些還沒反映。因果白板 Agent 會是獨立子圖（規劃中）。
- 想加角色？在 `decision.py` 加節點，並更新 `docs/MAP.md`。

## 6. 給 AI 助手的指引（請遵守）
- 優先建議「新增外掛檔案」，不要建議改 `graph.py` / `state.py` 除非真的必要。
- 回傳 State 時只回傳要更新的欄位。
- 不要繞過 `as_of`；不要在節點裡直接 `SELECT` 證據庫，請用 `store.search / store.get`。
- 不要把秘密（API key）寫進程式或提交到 Git。
- 改了流程要同步更新 `docs/MAP.md`。
- 用繁體中文回答，錯誤訊息要告訴使用者「哪裡出錯、怎麼修」。
