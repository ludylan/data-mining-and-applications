# AI 自主決策升級計畫 (AI Agent Upgrade Plan)

> 目的：讓 AI 真正參與選股與權重決策，並以「可回溯的因果論據」支撐。
> 狀態：計畫階段，尚未寫程式。最後更新：2026-10-27 20:30

---

## 1. 問題症結 (Root Causes)

| # | 症結 | 現況證據 | 後果 |
|---|---|---|---|
| P1 | **決策不是 AI 做的**：選股與權重由 Python 公式決定，LLM 只負責把理由寫漂亮（事後合理化） | `pm_agent.py` 的選股/權重段落無 LLM；LLM 只寫 `market_view` 與 `inferences` 文字 | 與 RULE-DEV-01（AI 自主決策）有落差；也沒有績效潛力 |
| P2 | **AI 沒有換股/加減碼提案權** | Day 2+ 邏輯為「全部續抱，最多換 1 檔」，由規則決定 | AI 無法因「漲多想減碼」「看到機會想加」而行動 |
| P3 | **因果鏈沒有真實資料**：昨日推論中的供應鏈說法來自模型自身知識，不是我們記錄的證據 | `LinkDossier` 程式存在，但實際帳本為空；`extra_signals` 為空 | 論據不可回溯、不可累積，審查時說不出依據 |
| P4 | **論據不分深度**：只有一層價量事實，沒有「基本必看」與「需要才深入」的區分 | 全部 O 都是價量/總經 | 要嘛資訊太少，要嘛一次塞太多 |
| P5 | **沒有跨日記憶**：帳本只存檔，隔天不讀回 | `dossier_ledger.json` 只寫不讀 | 每天從零開始，無法累積判斷 |
| P6 | **缺少籌碼與基本面資料** | 尚未接三大法人、月營收 | 論據類別單薄 |

## 2. 設計原則

1. **硬規則歸 Python、判斷歸 AI**：賽規（20~30 檔、2330≤25%、其餘≤10%、現金 0~25%、Active Share≥15%、千股整數、引用鏈）由沙盒把關；其餘讓 AI 提案。
2. **建議值而非鎖死**：個股權重區間改為「可超出，但必須寫理由」，真正上限只剩賽規。
3. **論據分深度、按需取用**：不一次餵全部，AI 看「菜單」自選。
4. **一切可回溯**：AI 看了哪些論據、為何下決定，全部進 `thought_trace.jsonl`。
5. **漸進上線**：每階段都保有可交件的保底版本。

## 3. 目標架構（在現有框架上修改）

### 3.1 現有框架（不動的部分）
```
collect_and_funnel → pm_agent_draft ⇄ sandbox_verify → finalize
```
M1 標的池、M2 行情收集、M3 漏斗與 S/O 編號、M5 沙盒八大鐵律、dashboard、Active Share 基準庫，**全部保留**。

### 3.2 要改的部分

```
collect_and_funnel
   → build_catalog        【新】建立本日論據目錄（菜單）
   → pm_agent_loop        【改】AI 提案迴圈（取代原公式式 pm_agent_draft）
         ├─ 看目錄，決定要取哪些論據 (L1 預載 / L2·L3 按需)
         ├─ 呼叫 fetch_evidence 取內容
         ├─ 形成提案：BUY / ADD / TRIM / SELL_ALL + 目標權重 + 理由 + 引用論據
         └─ 步數或呼叫上限到 → 強制收斂
   → apply_proposals      【新】把提案套成 decisions / no_trade_decisions
   → sandbox_verify       【沿用】不過就把「退回原因+補齊指引」送回迴圈
   → finalize             【改】另存 thought_trace、impact_ledger
```

### 3.3 新增資料結構

**論據目錄 (Evidence Catalog)**：設定檔 `catalog.yaml`，每筆只是一行菜單。

| 欄位 | 說明 |
|---|---|
| id | 例如 `pv.trend20` |
| category | 價量 / 供應鏈 / 籌碼 / 基本面 / 組合風險 |
| depth | L1 必看（預載）、L2 展開、L3 深入 |
| desc | 一句話說明 |
| params | 可帶參數（ticker、天數…） |
| cost | 預估大小（避免一次塞太多） |

新增資料源只要加一筆，不必改程式。

**影響帳本 (Impact Ledger)**：每筆因果影響一列。

| 欄位 | 說明 |
|---|---|
| event | 事件描述 |
| path | A → B 與傳導機制 |
| direction / magnitude | 看多或看空、強度 1~5 |
| rating | AI 評級（重要性 × 可信度） |
| source | 連結與日期 |
| decay | 時效衰減，過期自動降權 |

決策時取評級前 N 筆（例如前 10 / 20），不讀全部。這會接上現有 `LinkDossier` 並真正啟用它。

## 5. 可行性與風險

| 項目 | 評估 |
|---|---|
| 技術可行性 | **高**。LangGraph 條件迴圈已在用；新增的是目錄、取用工具、提案轉換。 |
| 成本 | **低~中**。Flash 單次很便宜，但迴圈會增加呼叫次數；設每日呼叫與步數上限。 |
| 輸出不穩（JSON 格式錯誤） | **中**。對策：強制結構化輸出、解析失敗自動重試、最終退回舊公式保底。 |
| AI 提案違規 | **低**。沙盒全面把關，違規只會被退回，不會送出。 |
| 提案過度交易（手續費損耗） | **中**。對策：在 prompt 與沙盒加每日換股上限與最小調整幅度。 |
| 資料來源穩定性（網頁爬取） | **中**。對策：快照存檔、失敗時降級為 L1。 |
| 時間 | A 階段可今晚完成；B、C 不影響明天交件。 |

### 保底機制
- 迴圈失敗或逾時 → 自動改走現有公式版，並在 trace 與 metadata 如實標示。
- metadata 的模型欄位必須反映「實際是否呼叫 LLM」，不得寫死。
